Keeping drafts written in several tabs

cobro-mcp · R-001 · In review · Gate 6

A note written in one tab disappeared when you edited a note in another tab. We fixed it by letting each tab replace only its own page's notes, and by having the sending tab put the page label on its notes itself.

Draft message handling moved from whole replacement to per-page replacement (R177); a new draft's page is now stamped from the sending tab instead of the global s.page, and ids being replaced are excluded from the kept list (Task 69 B1).

01 Problem · Writing in another tab wipes the first tab's note

Two tabs, a note in each. As soon as the note in the second tab was edited, the note written in the first tab was gone.

When two overlays (tabs) connected to the same session each send a draft message, one tab's message deletes the server draft created by the other tab.

Evidence fd91128 CHANGELOG.md Note: Drafts made in one tab are no longer wiped when you edit a draft in another tab

02 Observe · The draft message meant "replace everything"

Each tab sent "every note I have", and the receiving side swapped out the whole note box with it. The second tab didn't know about the first tab's note, so it overwrote the box without it.

The contract of OverlayMsg 'draft' was "replace everything with status draft", and SessionCore.setDrafts(batches) kept only non-draft batches and replaced all drafts at once.

Evidence dd6596f src/core/session.ts Note: code before the fix is at lines 34-35 of dd6596f's parent dd6596f src/core/types.ts

03 Attempt · Attempt 1: replace per page

Instead of swapping out the whole note box, only the notes of the sending tab's page get replaced. Each tab also sends only its own page's notes and merges the other tabs' notes into what it keeps.

Added page (location.href) to the draft message; setDrafts(batches, pageUrl) replaces only drafts where samePage holds. The overlay's flushDraft sends only current-page drafts and merges incoming state in server order.

Evidence dd6596f src/core/session.ts fd91128 src/overlay/index.ts Test: test/core/session.test.ts › setDrafts replaces drafts per page when a pageUrl is given (R177)

04 Fail · Open the tabs in another order and labels go wrong, notes double

Review stopped it. Open the first tab, then the second, then write a new note in the first tab — the note got the second tab's page label, and on the next save the same note turned into two.

New drafts were stamped with the server's global s.page (the tab that connected last), so labels went wrong. Resending the same id then left it in others (samePage mismatch) while also adding it to kept, duplicating it (review Task 69 B1).

Evidence 9af6e18 Note: Commit message: Task 69 B1 — stamp draft page with the sending tab's page, exclude replaced ids from the kept list 9af6e18 test/e2e/overlay.spec.ts:1281 Note: e2e changed to reproduce B1 (sequential tab switching)

05 Discovery · There was only one whiteboard

The problem wasn't how much of the box gets replaced, but not knowing which tab a note came from. The server kept a single shared whiteboard with only the last tab's name on it, and stuck that label on every new note.

The root cause was missing sender context, not replacement scope. setDrafts took a new draft's page from the global s.page, so with several tabs the label depended on connection order — and a wrong label also broke the replacement check (samePage).

Evidence 9af6e18 src/core/session.ts:57

06 Solution · The sending tab puts the label on

When a tab sends notes it includes its own page label, and the server puts exactly that label on new notes. Notes received in this message are always replaced regardless of their label, so nothing gets duplicated.

The draft message's page became a {url, title} object; setDrafts(batches, page) stamps drafts it sees for the first time with the message's page. Ids in keptIds are always excluded from others. The bridge passes page only when page.url is a string (backward compatible).

Evidence 9af6e18 src/core/session.ts:36-58 9af6e18 src/bridge.ts:37-38 9af6e18 src/core/types.ts:52

07 Edge case · Older tabs and the URL comparison rule

If an older tab sends without page info, everything is replaced as before. URLs that differ only after

A draft message without page falls back to whole replacement (backward compatible); old drafts without page are treated as the same page. samePage compares only origin+pathname+search and ignores the hash (R163).
