# 쉬운 설명 가이드 (2층 설명)

모든 scene은 같은 내용을 두 층으로 쓴다.

| 층 | 필드 | 독자 | 분량 |
|---|---|---|---|
| 쉬운 설명 | `plain` | 이 문제에 참여하지 않은 사람 — 새로 온 개발자, 현업 담당자(팩의 `business_readers`) | **2문장 이내** |
| 기술 설명 | `tech` | 코드를 고칠 개발자 | **3문장 이내** + 코드 15줄 이내 |

**쉬운 설명 = 이해하기 쉬운 설명이지, 쉬운 단어로 바꾼 설명이 아니다.** 비유로 바꾸면 현업은 읽기 편해도, 개발자는 비유를 다시 실제 개념으로 되돌려야 해서 오히려 헷갈린다. 그래서 기본 문체는 **명료형**이고, 현업 말로 쓰는 **현장형**은 필요할 때만 켠다.

## 1. 문체 고르기 (`plain_style`)

| 값 | 이름 | 언제 | 쓰는 말 |
|---|---|---|---|
| `clear` (기본) | 명료형 | 대부분. 특히 `audience`가 개발자 위주일 때 | 실제 용어 + 처음 한 번 풀이 |
| `field` | 현장형 | 현업·경영진이 주 독자일 때 (`audience`에 `business`·`exec`) | 독자가 매일 쓰는 업무 말 |

정하는 순서: 레시피 `plain_style` → 팩 `plain_style` → `clear`. 독자가 섞여 있으면 `clear`가 기본이다 — 현업용 레시피를 따로 원할 때만 `field`로 쓴다.

## 2. 공통 규칙 (두 문체 모두)

1. **눈에 보이는 현상**으로 시작한다. ("월말 마감 후 재고 수량이 장부와 다르다", "봉제선에서 옷이 벌어진다")
2. **사실과 어긋나는 비유 금지.** 독자가 아는 실제 공정·물건과 다르게 동작하는 비유는 오해를 만든다. (예: 시뮬레이션의 사전 배치를 "가봉"이라 부르면 가봉 공정이 틀린 것으로 읽힌다)
3. 비유는 **구조를 한 줄로 압축할 때만**, 장면당 한 번. 이름이나 원인을 비유로 대신하지 않는다. (좋은 예: "단계마다 재면 0인데 합치면 1.7cm가 어긋났다")
4. **작업 코드 금지** — 버전(v37), 실험 이름(expO), 플래그(`?taper=0`), 파일·함수 이름은 `tech`로.
5. 수치는 의미 있는 것 1~2개만, 단위를 붙인다. (건, 원, 초, mm, 사이즈명)
6. **다음 장면의 단서는 지우지 않는다.** 실패·관찰 장면에서 다음 시도의 근거가 된 사실은 `plain`에도 남긴다.
7. "~때문이다"로 원인을 단정하지 않는다. 원인은 `discovery`에서만 말한다.

## 3. 명료형 (`clear`) 규칙

1. **실제 이름을 쓴다** — 코드·문서에서 찾을 수 있는 이름(대응점, 프리랩, 인덱스, 캐시). 한국어 이름이 있으면 한국어로.
2. 낯선 용어는 **처음 나올 때 한 번만** 괄호로 풀이한다: "대응점(서로 꿰맬 점 짝)". 풀이는 팩 사전의 `note`, 없으면 `plain`을 쓴다.
3. 한 문장에 사실 하나, 원인 → 결과 순서로.

## 4. 현장형 (`field`) 규칙

1. 팩의 `business_readers`가 매일 쓰는 업무 말로 쓴다. 영문 약어·코드명·라이브러리명을 쓰지 않는다. (mesh, vertex, transform ✗)
2. 용어는 팩 사전의 `plain`으로 바꾼다. 로컬 팩 → `general` 사전 순으로 찾고, 없으면 팩의 `metaphor_source`에서 새로 만든 뒤 사전에 추가한다. ([domain-packs.md](domain-packs.md))
3. 업무 말로 정확히 옮길 수 없으면 비유 대신 "시뮬레이션 시작 전 배치 단계"처럼 하는 일을 그대로 적는다.

## 5. `tech` 작성 규칙

1. 정확한 용어를 쓴다. 비유를 섞지 않는다.
2. 재현 조건을 적는다. (입력 데이터, 환경, 파일, 버전)
3. 코드는 핵심 15줄 이내. 전체 코드는 `evidence`의 file:lines로 연결한다.

## 6. 예

| 구분 | 나쁜 예 | 좋은 예 |
|---|---|---|
| clear | 줄자 눈금이 너무 촘촘해 늘 꽉 찬 값만 나왔다 | 톱니 지표가 포화돼 있었다 — 측정 간격이 촘촘해 늘 최댓값이 나왔다. |
| clear | 바느질 짝이 4대1로 몰렸다 | 소매산만 대응점(서로 꿰맬 점 짝)이 진동 점 하나에 최대 4개 몰려 있었다. |
| clear | v35에서 ?taper=0으로 블렌드 하한을 내렸다 | 천을 어깨 높이로 끌어올리는 구간을 겨드랑이까지 넓혀 완만하게 했다. |
| clear | DB 인덱스 누락으로 풀스캔 발생 | 주문 테이블에 인덱스(찾아보기 목록)가 없어, 조회할 때마다 30만 건을 처음부터 훑었다. |
| field | race condition으로 재고 중복 할당 | 두 사람이 같은 좌석을 동시에 예약한 것처럼, 재고 하나가 두 주문에 잡혔다. |
| field | 천을 마네킹에 대충 둘러 핀 꽂은 상태 (실제 가봉과 다름) | 시뮬레이션을 시작하기 전, 천을 몸 둘레에 미리 놓아 두는 단계에서 이미 접혀 있었다. |
| 공통 | 좌표 불일치 이슈 발생 | 두 천의 끝이 4mm쯤 어긋나 있었다. |
| tech | 좀 느림 | 주문 목록 조회 p95 4.8s (주문 30만 건, 인덱스 없음). |

## 7. 점검 체크리스트

- [ ] 이 문제에 참여하지 않은 사람이 `plain`만 읽고 무엇이 왜 일어났는지 이해되는가?
- [ ] 사실과 어긋나는 비유가 없는가? 비유가 이름·원인을 대신하지 않는가?
- [ ] 버전·실험 이름·플래그·파일명이 `plain`에 없는가?
- [ ] (clear) 낯선 용어마다 처음 한 번 풀이가 있는가?
- [ ] (field) 영문 기술 용어가 없는가? 같은 용어에 레시피마다 다른 말을 쓰지 않았는가? (팩 사전 확인)
- [ ] `tech`에 재현 조건이 있는가?
